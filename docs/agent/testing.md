# 验证证据与完成判定

## 1. 任务状态不是测试颜色

| 任务状态 | 条件 |
|---|---|
| `COMPLETE` | 目标已交付且本任务全部必需验收满足，有对应候选版本与证据 |
| `PARTIAL` | 已有交付，但仍有未完成项或未满足的必需验收 |
| `BLOCKED` | 缺少必要权限、环境或决策，无法继续关键步骤 |

代码任务配置的 lint/test 默认必需，类型检查、构建、集成、UI、性能等由计划按风险补充。
lint 失败即使测试 GREEN 也不能 COMPLETE。明确需要的验收不得事后降级为可选来宣称完成。
纯审阅、规格起草和无产品行为变化的文档维护可用来源核对、结构/链接检查与人工审阅验收。
不适用必须说明任务依据；本应执行但缺环境的检查是未运行/受阻，不是不适用。

## 2. 保留测试五态

| 测试状态 | 条件，按从上到下的优先顺序判定 |
|---|---|
| `UNKNOWN` | 未配置、未启动、命令不存在、无法执行，或证据不足以可靠归类 |
| `TIMEOUT` | 已启动且被确认超过预算停止；不是成功，也不等同断言失败 |
| `RED` | 已运行且因测试失败、收集错误或验证错误而非零退出，注明失败原因 |
| `UNTESTED` | 退出码 0，但零测试、目标场景未执行或覆盖依据不足 |
| `GREEN` | 正常结束、退出码 0、预期场景实际执行且相关验收通过 |

先区分无法执行与已启动后失败，不把 shell 的“命令未找到”当作业务测试 RED。
多个检查分别报告，不能用一个 GREEN 抹掉其他失败。跳过测试的数量和原因必须披露。
对应测试依赖需求与行为映射，不依赖 Python/TS 文件名猜测，也不以断言数量证明测试未削弱。

## 3. 红绿证据

Bug/尚未实现的行为：优先证明修复前因目标原因失败，修复后通过，并跑相关回归。
新测试直接通过先核实功能是否已有、用例是否适用；补充覆盖与保持行为的重构不强制先失败。
环境、导入或语法错误不能冒充目标行为的失败证据；无法复现时明确说明，不制造假失败。
单元测试隔离网络、时间和随机性；集成/E2E 可用批准的临时环境，不接生产秘密或真实个人数据。
Mock 通过不等于真实联调；浏览器通过不等于原生宿主；截图不等于交互、可访问性或安全验收。

## 4. 证据记录

每项记录：候选提交或差异摘要、工作目录、完整命令、结果、退出码、发现/执行/通过/失败/跳过数、日志位置。
未运行不填写虚构退出码；日志先去敏，不能把秘密复制进 PR 或记忆。
命令用项目实际单次执行模式，确认没有进入 watch；仅清理本任务启动的进程。
环境差异、必需检查跳过、旧失败和剩余验收必须单列。

## 5. 本规则包检查边界

`check_bundle.py` 只检查结构与配置，不执行配置中的命令，也不评估任意自然语言的语义等价。
规则编号、正文非空、状态名称和有限行内链接检查是辅助措施，不能代替独立审查。
`validation/tests` 用临时目录运行检查器/安装器反例，不是跨模型 Agent 行为评测。
[行为场景](scenarios.md) 必须在真实工具里另行执行并记录；文档存在不等于场景通过。
CI 全绿必须核对候选版本、实际 job/step、未跳过的关键检查；不能只看可合并标志。
