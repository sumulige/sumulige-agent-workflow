# 核心工程原则

以下原则用于已授权范围内的设计与实现，不替代项目事实、任务范围或人类确认；适用流程与写入边界按[根规则](../../../AGENTS.md)及[分级流程](../workflow.md)执行。

**用户结果与价值优先：** 从真实用户的具体场景、现有做法和受阻原因出发定义需求，明确期望结果及其验证依据。区分事实、用户表达与待验证假设，综合评估使用成本、实现成本和维护成本，优先采用能够满足已确认需求的最小方案，并依据实际反馈持续调整。

1. **方案先行，架构与领域优先：** 复杂任务必须先调查现状并形成书面方案，明确业务目标、非目标、关键场景、约束与验收标准，区分已核实事实、现有缺陷和待验证假设。以此确定领域边界、模块职责、依赖方向和数据流，并写清实施顺序、关键依赖与阶段产物。设计应符合领域规律，支持长期维护与持续演进；不得以短期实现便利牺牲整体设计。设计覆盖问题全貌，实现围绕当前已确认需求；不做推测性抽象，抽象延迟到第二个真实用例出现时引入，单一场景直接实现。
2. **追求优雅的代码模块：** 模块应高内聚、低耦合，通过精简且稳定的接口封装内部复杂度，使职责、命名、依赖和扩展方式清晰自然；代码按单一职责拆分，单个文件不得超过 500 行，接近上限时应优先重构模块边界。
3. **保持边界与数据流清晰：** 协议模型、领域模型、持久化模型和视图模型不得相互混用；数据必须在边界处完成校验和独立转换，避免跨层共享可变状态。
4. **安全与隔离默认开启：** 所有功能均按多租户、多用户场景设计，明确认证、授权和数据隔离边界；遵循最小权限原则，任何外部输入均视为不可信，敏感信息不得进入代码、日志或响应。
5. **面向并发与故障设计：** 后端应主动考虑幂等性、竞态、事务边界、超时、取消、重试、背压和资源释放；不得通过无边界重试、吞错或隐式共享状态掩盖问题。
6. **保障完整前端体验：** 前端应控制渲染成本、异步状态和并发请求，保持清晰的 UI 结构；用户流程必须覆盖加载、空状态、错误、重试、反馈和可访问性。
7. **复用稳定的业务语义：** 优先复用已有模块和能力，但不要仅因代码外形相似而过早抽象；确需重复时，必须注释说明其独立演进或暂不抽象的原因。新增依赖前先核查项目已有依赖（根 `package.json` 与 `packages/` workspace）能否满足需求，不得臆断已有库缺少功能——先查阅文档和类型定义；确需引入时优先成熟且维护良好的库，不重复实现通用功能。
8. **持续维护方案，为未来维护者保留上下文：** 方案及相关工作文件应随任务推进持续更新。执行中对照已确认的目标与路径，避免局部问题带偏整体方向；出现新证据时，记录调整原因、影响范围与必要的确认依据。阶段完成或交接前，更新实际改动、验证结果、未解决问题和下一步。代码、注释、测试与架构文档是跨越时间的协作媒介：非显然的设计决策、兼容约束、已知缺陷和临时方案必须说明原因、风险及移除条件；技术债务关联可追踪任务，关键架构决策同步到 ADR，禁止留下缺少上下文的 TODO。
9. **确保变更可验证、可观测、可回滚：** 在方案中提前明确完成标准与验证方式，每项改动都应行为可测试、运行状态可观测、故障可定位，并兼顾向后兼容和回滚路径。以实际验证结果判断完成，保留可复核的证据，如实标明失败、未执行和未覆盖的范围；不得以步骤执行完毕代替目标达成。错误与日志必须保留诊断上下文，但不得泄露敏感信息。
10. **删除优于兼容：** 内部路径重构时直接删除过时实现，禁止新增兼容层、deprecated shim 或双写逻辑；对外契约（`/api/*` 等稳定接口、数据库迁移）的兼容性按协议契约单独评估，属于合同义务而非迁就旧代码。
