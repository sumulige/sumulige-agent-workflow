# 分级工作流程

## 1. 开始与授权

读取根规则、[项目配置](project.md) 和任务相关资料，记录任务目标、允许路径和验收方式。
代码任务先检查 Git 状态、分支、暂存区；无关未提交改动不阻塞，同一区域归属不明才协调。
不 stash、reset 或删除他人成果；没有 Git 的只读资料审阅不要求创建仓库。
一次批准涵盖已声明范围，不要求口令必须是“批准”。`[auto-approve]` 本身不是权限证明。

## 2. 任务分类

| 类型 | 流程与允许写入 |
|---|---|
| 只读审阅/调研 | 阅读、核实、报告；不写规格、记忆或业务文件 |
| 规格起草 | 只写明确授权的需求、设计、任务草稿；不自批，不修改产品 |
| 低风险维护 | 说明范围和适用验证后执行；不强制任务编号和三份规格 |
| 标准功能 | 需求验收 → 探索调用方与现有测试 → 计划 → 在授权范围内实现 → 验证 |
| Bug | 最小复现与预期行为 → 有界诊断 → 修复方案 → 授权内修复与回归 |
| 治理维护 | 仅修改用户指定的规则、配置、验证工具；未就绪时也适用，不扩大为产品授权 |

低风险不是按行数判定。鉴权、支付、个人数据、迁移、依赖、对外接口与生产操作须核对专门授权。
复杂任务必须先形成书面方案并按适用授权要求评审，执行过程中持续维护；已给出明确方案与执行授权时不重复申请同一审批。
缺少资料先利用可读仓库定位；确实没有规格且任务需要时再起草，不以无任务 ID 推断无规格。

## 3. 计划与规格权限

复杂任务或重要需求在进入实施方案前，先按[需求模板](../specs/_TEMPLATE/requirements.md)梳理用户价值：明确使用者、决策者与承担后果的人，说明具体场景、现有做法、目标结果、证据与假设、最小解决方式、成本取舍，以及验证和退出条件。
优先核实已有能力或更简单的流程能否满足需求；收益和指标没有依据时标为待验证，不用功能数量、代码量或工作时长代替用户结果。小改动可简写或引用已有结论，避免重复维护；只读任务在会话中说明，不因此取得写入或实施授权。
进一步明确触发需求的时刻、用户希望摆脱的负担及必须保留的控制；未表达的用途先作为待验证假设，以实际行为和用户确认核实。用真实使用证据判断负担是否减少，不能只凭询问次数下降就认定有效，也不能省略应有确认或隐藏问题。

方案要让用户与 AI 对目标、背景、实施路径和完成标准形成共同理解，并成为执行、调整与验收的依据。

1. **建立共识：把目标讲清楚。** 一句话可以表达方向，但不足以指导实现。明确解决什么问题、服务什么场景、包含与不包含哪些内容，以及怎样判断完成，提前澄清会影响架构和结果的细节。
2. **同步背景：把判断建立在事实上。** 围绕目标调查现有实现、相关资料和约束，梳理已有能力、现存缺陷与信息缺口，区分已核实事实和待验证假设，让双方基于同一背景作出决策。
3. **约束执行：让每一步都服务于目标。** 明确实施顺序、关键依赖和阶段产物，执行中持续对照目标。出现新证据时说明调整原因与影响；超出已批准范围的调整先确认，再更新方案和继续相关操作。
4. **持续留痕：让过程能够检查和接续。** 方案及相关工作文件随进展更新，记录关键决策、实际改动、验证结果、未解决问题和下一步，使中断、交接或复盘时仍能准确恢复上下文。

复杂任务在项目已授权位置维护方案，可引用已有规格与证据，不强制复制多份文件。只读任务在会话中写方案，未经授权不创建或更新工作文件；低风险维护仍按任务分类裁剪。

实现阶段 requirements.md、design.md、tasks.md 的需求主体默认只读。
当前任务 plan、复现测试及验证证据可在已批准范围内写入；完成勾选可按真实验收更新，但不自批依赖。
诊断阶段允许写复现文件须在授权范围里明确；仅只读诊断时提供复现建议，不偷偷运行写文件的工具。
合法需求变化导致已有断言改变，应同时解释需求依据、批准来源和回归影响，不一律称为作弊。

计划至少包含：目标与非目标、背景事实与待验证假设、文件范围、实施顺序与关键依赖、阶段产物与必需验收、风险与回滚、授权边界。
完成一个阶段、作出关键决策、调整路径或准备交接时，更新当前进展、证据、未解决问题和下一步。原目标与批准依据保留可追溯记录，不通过改写计划掩盖偏离。
超过 300 行是审查提醒；记录统计口径、生成文件和保持内聚提交的理由，不机械拆坏功能。

影响公共接口、数据模型、重要模块边界或依赖策略时，评估是否需要 ADR。
可以起草 [ADR](../adr/0000-template.md)，不得自行把 proposed 改为 accepted。

## 4. 实现、验证与暂停

遵守 [测试规则](testing.md)，先复现目标失败；补覆盖、重构不人为制造红灯。
每次运行记录命令与真实结果；环境/权限故障、已有失败与新引入失败分开处理。
先读取可用信息解决歧义；仅在授权、破坏性后果、关键需求冲突等无法消除时暂停相关部分。
已获批准的范围内继续，不反复索取同一批准；范围实质扩大或引入未批准高风险时重新确认。
同一失败原因连续三次且无新证据时停止重复尝试，保存事实、排除项和交接，不机械清空会话。

## 5. 交付与交接

按根规则报告任务状态、每项验收、候选提交/差异和未验证范围；执行完不自动开始新任务。
独立审查者记录候选版本、发现与复验；同一实现者的自检不得记录为独立通过。
并行任务隔离工作目录/分支，合并前检查冲突。默认记忆只给追加建议，不产生只读任务写入。

交接至少包含：当前目标、已批准范围、实际改动、已验证事实、失败与排除项、下一步和文件归属。
模型、提供商或工具版本不可得时写 unknown，不能推测；不记录密钥、原始个人数据或完整敏感日志。

默认 `explicit-request`：不自动提交。`after-validation` 是经人批准的长期本地提交策略。
明确要求提交到 GitHub 时，在任务分支提交并推送/创建 PR；不因此获准合并、部署或修改保护设置。
提交前核实工作区、暂存区、分支和最终差异；使用具体路径，但仍检查同一文件中的他人改动。
实现者自检不能冒充独立审查；独立审查应由另一执行者针对确定的候选版本完成并留痕。

默认只在报告中建议沉淀经验，使用 [记忆格式](../../.agent/memory.example.md)。
`append-authorized` 仅允许授权范围内追加经验证事实；只读任务不写记忆，记忆不授予权限。
并行 Agent 使用隔离工作区和各自交接记录，不能争写一个共享记忆文件。

交付按以下格式报告，未执行或不适用如实说明：

```text
TASK_STATUS: COMPLETE / PARTIAL / BLOCKED
CHANGED: 文件与作用；没有改动则写 none
CHECKS: 每项命令、工作目录、结果、退出码、执行数量和证据位置
TEST_STATUS: GREEN / RED / UNTESTED / TIMEOUT / UNKNOWN；不适用则单独说明理由
EVIDENCE: 候选提交或差异标识；未覆盖的验收
AUTHORIZATION: 使用的范围；偏离与批准记录
ACTORS: 实现者、工具/模型、独立审查者；工具未提供的信息写 unknown
GIT: 分支、提交/PR 或未提交文件；不得捏造 hash
NEXT: 遗留事项或 none
```
