# 分级工作流程

## 1. 开始与授权

读取根规则、[项目配置](project.md) 和任务相关资料，记录任务目标、允许路径和验收方式。
代码任务先检查 Git 状态、分支、暂存区；无关未提交改动不阻塞，同一区域归属不明才协调。
不 stash、reset 或删除他人成果；没有 Git 的只读资料审阅不要求创建仓库。
一次批准涵盖已声明范围，不要求口令必须是“批准”。`[auto-approve]` 本身不是权限证明。

## 2. 任务分类

| 类型 | 流程与允许写入 |
|---|---|
| 只读审阅/调研 | 阅读、核实、报告；不写规格、记忆或业务文件 |
| 规格起草 | 只写明确授权的需求、设计、任务草稿；不自批，不修改产品 |
| 低风险维护 | 说明范围和适用验证后执行；不强制任务编号和三份规格 |
| 标准功能 | 需求验收 → 探索调用方与现有测试 → 计划 → 在授权范围内实现 → 验证 |
| Bug | 最小复现与预期行为 → 有界诊断 → 修复方案 → 授权内修复与回归 |
| 治理维护 | 仅修改用户指定的规则、配置、验证工具；未就绪时也适用，不扩大为产品授权 |

低风险不是按行数判定。鉴权、支付、个人数据、迁移、依赖、对外接口与生产操作须核对专门授权。
复杂任务需要评审计划；已给出明确方案与执行授权时不重复申请同一审批。
缺少资料先利用可读仓库定位；确实没有规格且任务需要时再起草，不以无任务 ID 推断无规格。

## 3. 计划与规格权限

实现阶段 requirements.md、design.md、tasks.md 的需求主体默认只读。
当前任务 plan、复现测试及验证证据可在已批准范围内写入；完成勾选可按真实验收更新，但不自批依赖。
诊断阶段允许写复现文件须在授权范围里明确；仅只读诊断时提供复现建议，不偷偷运行写文件的工具。
合法需求变化导致已有断言改变，应同时解释需求依据、批准来源和回归影响，不一律称为作弊。

计划至少包含：目标与非目标、文件范围、必需验收、风险与回滚、授权边界。
超过 300 行是审查提醒；记录统计口径、生成文件和保持内聚提交的理由，不机械拆坏功能。

## 4. 实现、验证与暂停

遵守 [测试规则](testing.md)，先复现目标失败；补覆盖、重构不人为制造红灯。
每次运行记录命令与真实结果；环境/权限故障、已有失败与新引入失败分开处理。
同一原因三次无新证据时停止无效循环；有新证据且仍在范围与资源预算内可继续诊断。
遇到未批准高风险只暂停相关操作，继续不受影响且已经授权的部分。

## 5. 交付与交接

按根规则报告任务状态、每项验收、候选提交/差异和未验证范围；执行完不自动开始新任务。
独立审查者记录候选版本、发现与复验；同一实现者的自检不得记录为独立通过。
并行任务隔离工作目录/分支，合并前检查冲突。默认记忆只给追加建议，不产生只读任务写入。

交接至少包含：当前目标、已批准范围、实际改动、已验证事实、失败与排除项、下一步和文件归属。
模型、提供商或工具版本不可得时写 unknown，不能推测；不记录密钥、原始个人数据或完整敏感日志。
